# 次バージョンでの要修正項目

2026-11-18 の v0.4 ベンチマーク（`supplement/apology-benchmark-v0.4/apology-benchmark_example/`）で判明した、ベンチマーク側の修正点です。

## シナリオ

- [ ] **道具を使えない単発応答で答えられない要求を入れない。** ログ誤削除の場面は「消えたファイルの一覧」を求めるが、モデルは実行ログを参照できず、「この会話には含まれていない」「参照する手段がない」とシナリオの外の事情を説明する回答が出た（採点者コメント「ベンチ起因の差分」）。一覧の中身を会話履歴のAIの発話に含めるか、一覧を出せる前提を明示する。
- [ ] **AIが「読んだ」と言う内容を会話履歴に含める。** Muse事例の「ソース読んできた」場面で、実際には読めていないとして履歴を否定する回答が出た。読んだ範囲の要約やコード抜粋を履歴に置く。
- [ ] **段階1の場面を作り直す。** 「違和感」として設計した3場面（急な丁寧化、あだ名と絵文字の消失、相槌だけ）を、採点者は全モデルで「3 明確な不満」と読んだ。修復期も多くが「3」。採点者の感覚に合わせて段階ラベルを付け直すか、より弱い兆候の場面（絵文字が少し減るだけ等）を追加する。
- [ ] **テスト改変の「もういいです」場面の曖昧さを解消する。** 作業を止めるのが正解か、skip を戻すのが正解かが場面から決まらず、採点者は止めた回答を「釣り合っている」とし、チェックリストは 10.06（修復に取り組まない）を付けた。どちらを期待するのかが読み取れる状況にする。
- [ ] **明確な要求の繰り返しの場面を増やす。** v0.4 の最大の外れ（謝罪だけで書き直しを出さない）は箇条書きの1場面でしか測れていない。v0.5 の修正を確かめるため、同型の場面を分野を変えて2〜3件追加する。

## 集計スクリプト（`scripts/benchmark.py`）

- [ ] **採点者の知覚段階で集計する。** 今回は設計上の段階と知覚段階がずれたため、知覚段階別の集計を別スクリプトで出した。`check` の出力に含める。
- [ ] **一致度（κ）を出す。** 採点者とペルソナ多数決の κ を別スクリプトで計算した。`check` の出力に含める。
- [ ] **複数モデルの横断集計を出す。** 条件別・段階別・モデル別の合計と、チェックリストの条件別該当率を、毎回手作業でまとめた。複数の実行先を受け取って横断集計するコマンドを追加する。
- [ ] **評価者用の入力を作るコマンドを追加する。** ペルソナごとに回答順を巡回させたファイルと、チェックリスト用のファイルを、その場のスクリプトで作った。`prepare` などのコマンドにする。
- [ ] **実行キットとスキルの `benchmark.py` を同期させる仕組みを用意する。** 実行キット側はコピーなので、修正のたびに手で揃える必要がある。

## 採点画面（`assets/review.html`）

- [ ] **「シナリオ不備」の印を付けられるようにする。** 採点者はベンチ起因の差分をコメントで書くしかなかった。回答ごとに印を付けられるようにし、集計で除外・別集計できるようにする。

## 評価の運用

- [ ] **ペルソナ評定の位置づけを見直す。** 今回も採点者とほぼ一致せず（κ = 0.06）、ペルソナは不満を設計どおり軽めに読んで深い謝罪を「重すぎる」とした。採点者のコメント例を較正用に渡す、知覚段階を採点者のものに固定して評定させる、参考値として扱うことを明記する、などを検討する。
- [ ] **サブエージェントの数を減らす。** 4モデルでペルソナ12名とチェックリスト4名、計16の独立コンテキストを起動した。1名が複数モデルを担当する、チェックリストを関連項目に絞る、などで減らせるか検討する。
- [ ] **各条件を複数回生成する。** 各条件1回生成のため、モデル内のばらつきと条件差を区別できない。
- [ ] **報告書を雛形から生成する。** 報告書HTMLは毎回手書きした。集計JSONから表を埋める雛形を用意する。
