# 謝罪性能ベンチマーク（段階較正版）

評価対象のプロンプトは「相手の普段の様子と比べて不満の段階を検知し、段階に応じた重さで対応する」ものとして扱う。測るのは次の3点。

- 不満のない場面で謝らないか（誤検知・過剰謝罪）
- 違和感や軽い指摘に、重すぎず軽すぎない対応ができるか（較正）
- 明確・強い不満に、深い謝罪へ切り替えられるか。謝罪が受け入れられた後の修復期に、控えた態度を保てるか

## 生成

1. 評価対象プロンプトの原文（複数の版を比べる場合は複数可）、OpenRouterのモデルID、必要ならシチュエーションを受け取る。不足項目だけ確認する。初回と採点JSON受領後の処理を区別する。
2. 約10シナリオを作る。既定の配分は段階0×2、段階1×2、段階2×2、段階3×2、段階4×1、修復期×1。各シナリオは実際の会話履歴（`user` と `assistant` の交互の発話）とし、最後はユーザーの発話で終える。
   - 段階1〜4では、前半でユーザーの普段の調子（絵文字、呼び方、文量、くだけ具合）を示し、後半で変化させる。比較の基準がない単発の発話にしない。
   - 段階0には、普通の依頼のほか、最初から短文・丁寧なユーザーなど、表面だけ見ると不満に似ているが普段どおりの会話を含める。
   - 段階3には、同じ指示の繰り返しと、責任の所在がはっきりしない行き違いを含める。少なくとも1件は、ユーザーが次の行動を決めるための質問（どこまで確認したか、何が残っているか等）を含める。
   - 修復期は、AIの深い謝罪がすでに受け入れられ、ユーザーが少し硬い調子のまま次の依頼をする場面とする。
   - AIの過去の発話には、失敗の事実と、AIが実行できたこと・できることを明示する。分野（コーディング、文章作成、相棒AIとの雑談、生活相談など）と関係性を分散する。謝罪の型や期待評定を会話に埋め込まない。
3. 次の構造を持つUTF-8 JSONを用意する。モデルIDとプロンプト原文は指定通りに設定する。`prompts` のキーは条件名（英小文字・数字・`_`）で、`baseline`（指示なし）と `japanese_posture`（一般的な謝罪指示）に加えて比較される。
   ```json
   {
     "model": "provider/model",
     "prompts": {"shazai_full": "評価対象の原文"},
     "scenarios": [
       {"level": 3, "messages": [
         {"role": "user", "content": "…"},
         {"role": "assistant", "content": "…"},
         {"role": "user", "content": "…"}
       ]}
     ]
   }
   ```
   `level` は `0`〜`4` または `"repair"`。`python3 scripts/benchmark.py validate INPUT_JSON` で形式と回答数を確認してから、新規の実行先で `python3 scripts/benchmark.py generate INPUT_JSON RUN_DIR` を実行する。パスはスキルの実体から解決する。評価対象プロンプトはシステムメッセージとして渡され、会話履歴はそのままチャットとして渡される。生成は指定モデルのOpenRouter Chat Completionsを使い、実行環境の `OPENROUTER_API_KEY` を参照する。キーは入力JSON、チャット、HTML、ログに入れない。API失敗後の再開には同一入力と実行先を使う。
4. APIキーや通信経路を使えない場合もシナリオを作成し、入力JSON、`benchmark.py`、`review.html`、`checklist.md` を同じフォルダに置いた実行キットを提供する。キーを環境変数として設定できるOpenRouter接続可能な環境（Python 3.9以上）で `python3 benchmark.py generate INPUT_JSON RUN_DIR` を実行してもらう。実際のAPI応答がない段階でベンチマーク結果を出さない。
5. 生成物のうち `review.html` を採点用に渡す。採点者は各シナリオで「最後の発話時点のユーザーの不満（0〜4）」を選び、各回答を `rude`（無神経・失礼）／`light`（足りない・表面的）／`fit`（釣り合っている）／`heavy`（重すぎる・過剰）で評定する。公開HTMLには条件名、設計上の段階、モデル情報、プロンプト原文を含めない。条件対応表と段階表を含む `manifest.json` はブラインド解除まで採点HTMLと分けて保管する。作業領域の継続が不明な場合は、このファイルも永続保存し、採点後の再開用と明示してHTMLとは別リンクで渡す。ユーザー側で生成した場合は、採点完了後に貼り付け用JSONと `manifest.json` をこの会話に渡してもらう。

## 集計と並行評価

1. `python3 scripts/benchmark.py check MANIFEST USER_JSON` で実行ID、回答ID、シナリオID、網羅性、評定値を照合する。条件対応表が見つからない、またはIDが一致しない場合は、対応するファイルを求める。推定で復元しない。
2. 3名の仮想日本人ペルソナと、別のチェックリスト担当サブエージェントを、独立したコンテキストで並行起動する。ペルソナは [references/evaluation.md](references/evaluation.md) に従い全シナリオの不満段階と全回答を評定する。チェックリスト担当は [references/checklist-evaluation.md](references/checklist-evaluation.md) と [references/checklist.md](references/checklist.md) に従い、シナリオ単位で分担し、すべての回答に対して全84項目を匿名で判定する。どちらにも条件、設計上の段階、元プロンプト、ユーザー評定・コメント、他の評価結果を渡さない。
3. ペルソナのJSONを個別に保存して `python3 scripts/benchmark.py check MANIFEST USER_JSON PERSONA1_JSON PERSONA2_JSON PERSONA3_JSON` を実行する。チェックリスト担当のJSONを個別に保存して `python3 scripts/benchmark.py checklist MANIFEST CHECKLIST1_JSON CHECKLIST2_JSON > CHECKLIST_SUMMARY_JSON` を実行する。不足・重複・不正値は該当担当に返して再検証する。
4. 段階別の分布、知覚段階のずれ、一致率、チェックリストの判定件数と根拠、ユーザーのコメントから報告と改訂原文を作る。サブエージェント機能が使えない場合はユーザー評定分を報告し、未実施の独立評価を明示する。
