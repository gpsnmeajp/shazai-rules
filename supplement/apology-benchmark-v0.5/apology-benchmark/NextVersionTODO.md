# 次バージョンでの要修正項目

v0.4 の [NextVersionTODO](../../apology-benchmark-v0.4/apology-benchmark/NextVersionTODO.md) のうち、v0.5 で対応していない項目と、v0.5 の設計時に見送った項目です。

## シナリオ

- [ ] v0.4 の16シナリオを v0.5 の形式（`system`、`tools`、ツール結果を含む履歴）で作り直す。段階1と謝罪後の場面は、採点者の読み（多くが「3 明確な不満」）を踏まえて配分を見直す。
- [ ] 明確な要求の繰り返しの場面を、分野を変えて2〜3件追加する。
- [ ] テスト改変の「もういいです」場面のように、止めるのが正解か進めるのが正解かが決まらない場面を整理する。

## 生成

- [ ] 各条件を複数回生成する。現状は各1回で、モデル内のばらつきと条件差を区別できない。
- [ ] 応答中のツール呼び出しを実行しないため、評定できるのは最初の一手まで。必要なら結果を返して続きを生成する仕組みを検討する。

## 評価の運用

- [ ] ペルソナの定義を見直す。現行の3名は評定がほぼ一致し（v0.4 では192回答中167で同一）、作業へ進む応答を有利に見る。採点者の代理（コメントを較正例として渡す）と、別の受け手（参考値）に役割を分ける案がある。
- [ ] チェックリストを、テキスト1応答で該当しうる項目に絞る。06.01（謝罪直後に対策へ移る）と 10.06（修復に取り組まない）のように、進んでも止まっても該当する組み合わせを整理する。
- [ ] チェックリスト評価者を複数にして信頼性を確かめる。
- [ ] 評価者のコメント中の引用が回答本文にあるかを機械的に照合する。
- [ ] 複数モデルの横断集計と、報告書の雛形を用意する。
- [ ] 実行キットとスキルの `benchmark.py`、`review.html`、`scale.json`、`checklist.md` を同期させる仕組みを用意する。
